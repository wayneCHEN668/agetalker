AgeTalker 长时对话改造 — 实现备忘录

针对「一小时对话能否前后连贯、事实一致」的问题所做的五阶段改造。 本文记录实现中的设计决策、对设计文档的偏离、取舍，以及待确认的问题。

1. 出发点

原管线是逐轮反应式的：每轮独立完成「路由分类 → 选策略 → 生成回复」， 会话级状态只有三份（对话历史、已用策略、上轮类别）。这在 3~5 分钟的短对话里工作良好， 但目标场景是一次可能持续一小时的陪伴对话。

核心死锁

LLM_MAX_HISTORY_TURNS=6 意味着模型只能看到约 3~5 分钟的对话。这与 templates.py 的「事实红线」形成死锁：红线禁止编造老人没说过的事， 但第 40 分钟的模型根本不知道第 5 分钟提过的人名。于是它只剩两条路—— 反问「那位是谁」（对老人来说就是「你没在听」，陪伴场景里最伤人的失败）， 或者顺着语气编（正好违反红线）。

2. 各阶段改动概览

3. 关键设计决策

3.1 只从老人的原话抽取事实，不从 AI 回复抽 最重要

AI 的回复是生成出来的，可能已经含有幻觉。如果把它当事实写进台账，等于把幻觉 「洗」成记忆——之后每一轮都会被当作真事引用，错误持续放大且再也无法追溯来源。 因此 observe_turn() 只接收 user_text，签名上就不给传回复的机会。

3.2 事实抽取放后台，而非搭车路由调用

搭车路由（扩展其输出 JSON）不增加网络往返，但会推高 ROUTER_MAX_TOKENS 并延长关键路径上的路由延迟。改为在 done 之后用 asyncio.create_task 触发，当轮回复延迟完全不受影响。 代价：本轮说的事实从下一轮开始可用——对连贯性无实质影响。

3.3 台账跨会话、摘要仅会话内

台账是「关于这个人的稳定事实」，摘要是「这次聊天的叙事线」，生命周期本就不同。 会话结束时摘要以精简形式留档进台账的 session_summaries，供跨天回指。

3.4 策略统计改为紧凑聚合

原实现存一条条原始记录并按最近 8 条截断。一小时内某类别可能被访问 30 次以上， 早期记录会滚出窗口，路由于是「忘了」开头用过什么，第 50 分钟又从第一条策略重做。 改为按 strategy_id 聚合成「次数 + 最近一次效果」后，条目数天然受限于 该类别的策略条数（≤6），再长的会话也不会滚掉。

3.5 用情绪 valence 作为策略推进的闭环信号

情绪服务算出的 valence 是判断「上一步干预有没有起作用」唯一的客观信号， 但它以前只送给生成模型当语气参考，从未送达路由。现在两轮之间比对 valence，归为 好转 / 持平 / 下降 三档喂给路由，并在 prompt 里给出推进门控规则 （好转→可推进；持平→再给一轮；下降→换同阶段另一条）。

4. 对设计文档（STEP3）的偏离

4.1 危机轮次仍然写入对话历史（偏离 §9.3）已确认采纳

规范要求「危机触发后当前轮次对话历史不保存，避免污染后续上下文」。 本实现没有照做：抹掉危机轮会让紧接着的下一轮丢失刚刚发生的最重要语境， 反而更危险。

采取的折中：保留在对话历史中（保证连贯），但排除在台账与摘要的持久化之外 （_schedule_memory_work 在 crisis=True 时跳过 observe_turn）， 避免危机内容长期留存并被跨会话回指。此项已有测试覆盖 （test_normal_turn_feeds_memory_but_crisis_turn_does_not）。

已确认采纳此折中。

4.2 危机警惕期只按轮数衰减，不做「情绪好转即解除」（偏离规划）

原计划写的是「路由判定情绪明确好转时提前清零」。实现时改为只按轮数自然衰减： 刚经历过高危信号的人，表面上说「我没事了」恰恰是最典型的表现，用这个信号提前解除警惕， 等于在最不该松手的时候松手。多警惕两轮的代价远小于反过来。

4.3 危机界面用暖琥珀色，而非警报红（对 §9.2 的解释）

规范写的是「温暖橙色（安全感色调）」，本实现照此执行并明确了理由： 看到这块屏幕的是正处在危机中的老人本人，对他闪红色只会加重恐慌。 红色（Design.colors.crisis）只用于「联系护理员」按钮的点缀。

4.4 不硬性禁用「结束对话」（对 §9.2 的解释）

规范要求危机时「禁用结束对话按钮，防止用户独处」。直接禁用等于把人困在界面里， 同样有害。改为：危机时结束确认弹窗换一套挽留说法，主按钮变成「叫护理员」。 目的是不让他一个人待着，而不是不让他退出。

5. 取舍

5.1 逐句 TTS 的最小片段长度

恢复首句流水线后，若每凑够一句就发一次合成，CARE 的 C 步骤（「哦，是啊。」这类 ≤10 字短句）会单独变成一次请求——多一次往返，语流也被切碎。 折中：攒到 MIN_TTS_CHUNK_CHARS = 12 才发，把过短的 C 与紧随的 A 并成一次合成。 首次出声仍远早于整段生成结束。

5.2 结束对话的等待时间 已修复

第一版用的是「等 6 秒再清屏」的硬编码值。复核时发现这是个真缺陷，不是打磨项： await fetchClosing() 等的是文字流结束，而语音由 useTTS 在后台排队播放。 收尾提示词要求三四句话（约 60~80 字），中文 TTS 每秒约 4~5 字，需要 13~18 秒才念得完—— 6 秒几乎必然把告别语切在半句上，恰恰是最不该出岔子的那一句。

已改为接上 useTTS 的 onPlaybackDone（该回调早就存在，只是从未接线）。

5.3 台账 schema 精简

规划里曾包含 sensitive（不该主动提及的话题）字段。实现时去掉了： 没有可靠机制去填充它，留一个永远为空的字段只会增加复杂度。需要时再加。

6. 过程中发现并修复的问题

6.1 长对话测试的假阳性（自查发现）

最初的长对话测试用「建国」作为验证人名，而我在改写事实红线时正好也用了「建国」 举例。于是断言匹配到的是模板的固定文案而非真正的记忆——测试看着通过了， 其实什么都没验证到。是对照组测试（关掉记忆后断言该名字消失）先炸了才暴露出来。

修复：模板举例改为不含具体人名；测试改用不会出现在任何模板里的名字， 并增加一条守卫断言 test_person_name_is_not_in_any_prompt_template， 以后谁再换名字撞车会先炸在这里。

6.2 收尾时序的竞态（接线 onPlaybackDone 时发现）

光接上 onPlaybackDone 还不够。语音播放常常比 LLM 生成快， 播放队列可能在两段文字之间就先空了一次，onPlaybackDone 会提前触发—— 只听它照样会把告别掐断。反过来只等文字流结束，则会在语音还剩十几秒时就清屏。

最终做法：收尾条件必须同时满足「文字流已结束」且「语音队列已播空」， 函数做成幂等，两个来源都调用它，谁最后满足条件谁真正执行。 为此给 useTTS 加了一个与 isPlaying 同步的 isPlayingRef （state 在回调闭包里会读到旧值）。另加 45 秒兜底定时器， 防止告别一句都没播出来时界面卡住回不去。

6.3 既有测试的 mock 缺陷

test_crisis_skips_routing 里 mock_route.return_value 是二元组， 而 _route_category 返回三元组。它一直「通过」只是因为危机拦截使该 mock 从未被调用。一旦哪天危机拦截失效，这个测试会以 unpack 报错的形式挂掉， 掩盖真正的问题。已改为三元组。

6.4 测试污染仓库

危机相关的测试会真的走到事件分发，每跑一次就往 backend/data/crisis_events/ 里写一批真实 JSON 文件。 已加 autouse fixture 拦住 _write_event，并清理了本次产生的 22 个文件 （六月那批已被 git 跟踪的保留未动）。

6.5 虚拟环境不可用

backend/.venv 是在另一台机器上创建的（home 指向 D:\Program Files\python311，command 里的路径是 E:\MyDoc\APP\...）， 基础解释器已不存在，任何 python.exe 调用都直接失败。 本机有版本完全一致的 Python 3.11.9，且 venv 内 220 个包完好。 已修改 pyvenv.cfg 的 home / executable 两行指向本机安装路径。 这是对环境的改动，特此说明。

7. 验证情况

  • 35 个后端单测全部通过（test_llm_service.py 16 + test_memory_service.py 13 + test_long_conversation.py 6）。
  • 核心断言：test_early_fact_still_known_at_turn_100 —— 120 轮回放中， 第 5 轮提到的人物在第 100 轮仍出现在注入生成模型的 prompt 里，且已落盘。
  • 对照断言：test_history_window_alone_would_have_lost_it —— 关掉记忆后 同一名字在第 100 轮消失，证明上面那条测的确实是长程记忆的功劳。
  • 前端：npx tsc --noEmit 无错误。
  • 真实 API 冒烟：抽取 prompt 对「我老伴桂芬走了三年了，她生前最爱听黄梅戏」 返回结构正确的 JSON；对纯闲聊句「嗯，今天天气还行」返回三个空数组， 说明「宁可少记，不能记错」的约束确实生效。

尚未做的验证

没有跑过真实的长时端到端对话（需要真人对着麦克风说 20 分钟以上）。 ASR 断线重连的路径是按 SDK 回调语义实现的，但没有在真实断网条件下验证过—— 这是目前最需要实机确认的一处。

8. 已确认的决定

问题结论
危机轮次的历史处理（4.1） 采纳该折中：保留在对话历史中，但不写入长程记忆。
台账的存储与保留 当前明文 JSON、永久保留，可接受。未来迁移到数据库并加密存储。
elder_id 的来源 当前 localStorage 方案可接受。应用未来部署为手机 App， 打开即是老人本人使用，属单用户场景，不需要「选择老人」的界面。
收束等待时间（5.2） 已修复：改为等语音真正播完（详见 5.2 与 6.2）。

9. 实机测试后的修复（第二轮）

真人对着 App 聊过之后暴露出四个问题，其中两个是本次改造自己引入的。

9.1 AI 提到了老人从没说过的人和事 严重

排查过程先排除了两个嫌疑：台账里只有一个没有任何 notes 的名字，不足以支撑编造； 策略库里所有带引号的内容都是提问和通用说法，没有一条断言老人的生活事实。

真凶是事实红线自己的举例。那段文字的用意恰恰是禁止编造，但它写成了：

- 好的回应（只回应已说内容，不新增事实）："五十年的邻居情分，搬都搬不走啊。"
- 好的回应（自然引用记着的事）："你早先说过你俩是五十年的老邻居了。"

四条示例里塞满具体的人和事（老王、五十年邻居、往医院跑），其中两条还标着 「好的回应」。模型手上没素材时就把这些当可用材料说了出来——典型的 few-shot 内容泄漏。其中第二条是本次改造新加的，它更毒：教会了模型 「你早先说过 X」这个凭空断言老人说过某事的句式。

修复：给举例加前提锚点 + 大声声明「这是另外一段对话，一个字都不许搬进你的回复」； 删掉「你早先说过……」那条；新增「开口前的自查」——句中出现任何具体人名/地点/ 时间/数字/事件，先自问来源，两样都不是就删掉。

同时堵上了第二条泄漏通道：台账定了「只从老人原话抽取」的铁律， 但摘要那条漏了——_summarize_input 原本把 AI 的回复也喂给摘要模型， AI 编的话会被摘要吸收成「聊过的事」，之后每轮作为事实注入，幻觉就这么洗白成记忆。 现在只传老人自己的话。

9.2 标点自适应窗口是错的 自己引入

为解决「一句话被切成两三句」，第一版按尾部标点自适应合并窗口：以句号结尾就 只等 350ms。实机转写给出了反证——「上面写的名字。叫王翠芬。」， 句号出现在一句连贯话的中间。

原因：ASR 的标点是按韵律停顿插的，不是语义终止信号。老人边想边说， 思考的停顿会被插成句号。于是这条规则恰好在他话说到一半停顿时判定说完了， 反而更容易切断——启发式在老年人语音上是反向工作的。

修复：去掉标点判断，改单一窗口（默认 1400ms），云端 VAD 从 1500 降到 1000ms （让云端放开切，轮次边界由我们这层定）。唯一可靠的信号是「他又开口了」。

9.3 句间卡顿 自己引入

Stage 1 做首句 TTS 流水线时，playOnce 取完音频后 await 到播放结束 才返回，而 processQueue 又 await 它才取下一句。于是下一句的合成延迟 （网络往返 + CosyVoice 会话启动，300~800ms）被原样暴露成句间空白—— 等于把「开头一次长静默」换成了「中间好几次短卡顿」。

修复：把取音频与播音频解耦，取完立即返回、下一句请求马上发出， 排期交给 nextStartTimeRef，WebAudio 自己把前后两段无缝接起来。 配套把打断用的「已播出多少」从「累计字符串 + 当前段」改成播放时间线数组， 因为多段现在是预排期的，原来的顺序假设不成立了。

9.4 一轮发言产生两条回复

与 9.2 独立的 bug：第二段发言到达时第一条回复还在生成，系统没有作废它， 两条并行跑完都显示出来，内容大半重复。

修复：新一轮用户发言到达时，若上一条回复仍在生成或播放，就地作废—— 中止 SSE、停 TTS、屏幕上那半条按实际说出口的截断（一字未出就整条撤掉）， 并等后端历史截断完成再发下一轮请求（否则新用户消息先进历史， 截断会找不到目标）。复用了打断功能已有的零件。

这两个修复是互补的，但 9.4 才是硬保证：合并窗口再怎么调都可能漏， 而作废机制保证无论切成几段，最终只有一条回复，且它拿到的是完整的话。

9.5 语音打断（barge-in）

TTS 播放期间麦克风帧此前被整个丢弃（防止 AI 自己的声音被转写成用户输入、 形成自问自答的死循环）。现在改为：仍不发往云端，但本地做能量检测—— 浏览器 AEC 已把喇叭声消掉大半，这时出现持续高能量大概率是有人在说话。

三重防误触发：自适应阈值（开头 300ms 测房间本底，阈值 = 本底 × 3.5，另有绝对下限）、 起始 500ms 保护期（防上一句尾音）、连续 3 帧才算（滤咳嗽/关门/电视爆音）。 另有约 770ms 预缓冲，打断成立时先补发，否则老人开口的头几个字会被检测耗掉。

调参集中在 mobile/constants/BargeIn.ts，带 ENABLED 总开关。 阈值必须在真实房间里调——养老院有电视和走廊动静，误触发导致 AI 动不动把话说到一半停掉，比不能打断更糟。

10. 后续可做的事

  • 台账迁移到加密数据库（已确认的方向）。届时只需替换 MemoryService._load / _save 两个方法， 其余逻辑与存储无关，不需要改动。
  • 护工侧的台账查看与订正入口：抽取难免有偏差， 目前没有人工纠正的途径，错了就一直错着。
  • 实机验证 ASR 断线重连（见第 7 节，最需要确认的一处）。
  • 输出侧事实校验：9.1 的修复是 prompt 约束，只降低概率、不是硬保证。 真要保证得在生成后抽出回复中的专有名词，跟「老人说过的话 + 台账」比对， 发现新增的就重新生成。需要额外一次调用或本地 NER，成本不低。
  • 打断阈值实测调参（见 9.5）与 合并窗口实测调参（见 9.2）， 两者都只能在真实房间/真人对话里定。
  • 幻觉的历史放大效应：一旦某轮编造进了对话历史， 后续几轮会把它当既成事实继续引用，越滚越实。目前只能靠重开会话清除， 没有自动检测机制。

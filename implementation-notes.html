AgeTalker 长时对话改造 — 实现备忘录

针对「一小时对话能否前后连贯、事实一致」的问题所做的五阶段改造。 本文记录实现中的设计决策、对设计文档的偏离、取舍，以及待确认的问题。

1. 出发点

原管线是逐轮反应式的：每轮独立完成「路由分类 → 选策略 → 生成回复」， 会话级状态只有三份（对话历史、已用策略、上轮类别）。这在 3~5 分钟的短对话里工作良好， 但目标场景是一次可能持续一小时的陪伴对话。

核心死锁

LLM_MAX_HISTORY_TURNS=6 意味着模型只能看到约 3~5 分钟的对话。这与 templates.py 的「事实红线」形成死锁：红线禁止编造老人没说过的事， 但第 40 分钟的模型根本不知道第 5 分钟提过的人名。于是它只剩两条路—— 反问「那位是谁」（对老人来说就是「你没在听」，陪伴场景里最伤人的失败）， 或者顺着语气编（正好违反红线）。

2. 各阶段改动概览

3. 关键设计决策

3.1 只从老人的原话抽取事实，不从 AI 回复抽 最重要

AI 的回复是生成出来的，可能已经含有幻觉。如果把它当事实写进台账，等于把幻觉 「洗」成记忆——之后每一轮都会被当作真事引用，错误持续放大且再也无法追溯来源。 因此 observe_turn() 只接收 user_text，签名上就不给传回复的机会。

3.2 事实抽取放后台，而非搭车路由调用

搭车路由（扩展其输出 JSON）不增加网络往返，但会推高 ROUTER_MAX_TOKENS 并延长关键路径上的路由延迟。改为在 done 之后用 asyncio.create_task 触发，当轮回复延迟完全不受影响。 代价：本轮说的事实从下一轮开始可用——对连贯性无实质影响。

3.3 台账跨会话、摘要仅会话内

台账是「关于这个人的稳定事实」，摘要是「这次聊天的叙事线」，生命周期本就不同。 会话结束时摘要以精简形式留档进台账的 session_summaries，供跨天回指。

3.4 策略统计改为紧凑聚合

原实现存一条条原始记录并按最近 8 条截断。一小时内某类别可能被访问 30 次以上， 早期记录会滚出窗口，路由于是「忘了」开头用过什么，第 50 分钟又从第一条策略重做。 改为按 strategy_id 聚合成「次数 + 最近一次效果」后，条目数天然受限于 该类别的策略条数（≤6），再长的会话也不会滚掉。

3.5 用情绪 valence 作为策略推进的闭环信号

情绪服务算出的 valence 是判断「上一步干预有没有起作用」唯一的客观信号， 但它以前只送给生成模型当语气参考，从未送达路由。现在两轮之间比对 valence，归为 好转 / 持平 / 下降 三档喂给路由，并在 prompt 里给出推进门控规则 （好转→可推进；持平→再给一轮；下降→换同阶段另一条）。

4. 对设计文档（STEP3）的偏离

4.1 危机轮次仍然写入对话历史（偏离 §9.3）已确认采纳

规范要求「危机触发后当前轮次对话历史不保存，避免污染后续上下文」。 本实现没有照做：抹掉危机轮会让紧接着的下一轮丢失刚刚发生的最重要语境， 反而更危险。

采取的折中：保留在对话历史中（保证连贯），但排除在台账与摘要的持久化之外 （_schedule_memory_work 在 crisis=True 时跳过 observe_turn）， 避免危机内容长期留存并被跨会话回指。此项已有测试覆盖 （test_normal_turn_feeds_memory_but_crisis_turn_does_not）。

已确认采纳此折中。

4.2 危机警惕期只按轮数衰减，不做「情绪好转即解除」（偏离规划）

原计划写的是「路由判定情绪明确好转时提前清零」。实现时改为只按轮数自然衰减： 刚经历过高危信号的人，表面上说「我没事了」恰恰是最典型的表现，用这个信号提前解除警惕， 等于在最不该松手的时候松手。多警惕两轮的代价远小于反过来。

4.3 危机界面用暖琥珀色，而非警报红（对 §9.2 的解释）

规范写的是「温暖橙色（安全感色调）」，本实现照此执行并明确了理由： 看到这块屏幕的是正处在危机中的老人本人，对他闪红色只会加重恐慌。 红色（Design.colors.crisis）只用于「联系护理员」按钮的点缀。

4.4 不硬性禁用「结束对话」（对 §9.2 的解释）

规范要求危机时「禁用结束对话按钮，防止用户独处」。直接禁用等于把人困在界面里， 同样有害。改为：危机时结束确认弹窗换一套挽留说法，主按钮变成「叫护理员」。 目的是不让他一个人待着，而不是不让他退出。

5. 取舍

5.1 逐句 TTS 的最小片段长度

恢复首句流水线后，若每凑够一句就发一次合成，CARE 的 C 步骤（「哦，是啊。」这类 ≤10 字短句）会单独变成一次请求——多一次往返，语流也被切碎。 折中：攒到 MIN_TTS_CHUNK_CHARS = 12 才发，把过短的 C 与紧随的 A 并成一次合成。 首次出声仍远早于整段生成结束。

5.2 结束对话的等待时间 已修复

第一版用的是「等 6 秒再清屏」的硬编码值。复核时发现这是个真缺陷，不是打磨项： await fetchClosing() 等的是文字流结束，而语音由 useTTS 在后台排队播放。 收尾提示词要求三四句话（约 60~80 字），中文 TTS 每秒约 4~5 字，需要 13~18 秒才念得完—— 6 秒几乎必然把告别语切在半句上，恰恰是最不该出岔子的那一句。

已改为接上 useTTS 的 onPlaybackDone（该回调早就存在，只是从未接线）。

5.3 台账 schema 精简

规划里曾包含 sensitive（不该主动提及的话题）字段。实现时去掉了： 没有可靠机制去填充它，留一个永远为空的字段只会增加复杂度。需要时再加。

6. 过程中发现并修复的问题

6.1 长对话测试的假阳性（自查发现）

最初的长对话测试用「建国」作为验证人名，而我在改写事实红线时正好也用了「建国」 举例。于是断言匹配到的是模板的固定文案而非真正的记忆——测试看着通过了， 其实什么都没验证到。是对照组测试（关掉记忆后断言该名字消失）先炸了才暴露出来。

修复：模板举例改为不含具体人名；测试改用不会出现在任何模板里的名字， 并增加一条守卫断言 test_person_name_is_not_in_any_prompt_template， 以后谁再换名字撞车会先炸在这里。

6.2 收尾时序的竞态（接线 onPlaybackDone 时发现）

光接上 onPlaybackDone 还不够。语音播放常常比 LLM 生成快， 播放队列可能在两段文字之间就先空了一次，onPlaybackDone 会提前触发—— 只听它照样会把告别掐断。反过来只等文字流结束，则会在语音还剩十几秒时就清屏。

最终做法：收尾条件必须同时满足「文字流已结束」且「语音队列已播空」， 函数做成幂等，两个来源都调用它，谁最后满足条件谁真正执行。 为此给 useTTS 加了一个与 isPlaying 同步的 isPlayingRef （state 在回调闭包里会读到旧值）。另加 45 秒兜底定时器， 防止告别一句都没播出来时界面卡住回不去。

6.3 既有测试的 mock 缺陷

test_crisis_skips_routing 里 mock_route.return_value 是二元组， 而 _route_category 返回三元组。它一直「通过」只是因为危机拦截使该 mock 从未被调用。一旦哪天危机拦截失效，这个测试会以 unpack 报错的形式挂掉， 掩盖真正的问题。已改为三元组。

6.4 测试污染仓库

危机相关的测试会真的走到事件分发，每跑一次就往 backend/data/crisis_events/ 里写一批真实 JSON 文件。 已加 autouse fixture 拦住 _write_event，并清理了本次产生的 22 个文件 （六月那批已被 git 跟踪的保留未动）。

6.5 虚拟环境不可用

backend/.venv 是在另一台机器上创建的（home 指向 D:\Program Files\python311，command 里的路径是 E:\MyDoc\APP\...）， 基础解释器已不存在，任何 python.exe 调用都直接失败。 本机有版本完全一致的 Python 3.11.9，且 venv 内 220 个包完好。 已修改 pyvenv.cfg 的 home / executable 两行指向本机安装路径。 这是对环境的改动，特此说明。

7. 验证情况

  • 35 个后端单测全部通过（test_llm_service.py 16 + test_memory_service.py 13 + test_long_conversation.py 6）。
  • 核心断言：test_early_fact_still_known_at_turn_100 —— 120 轮回放中， 第 5 轮提到的人物在第 100 轮仍出现在注入生成模型的 prompt 里，且已落盘。
  • 对照断言：test_history_window_alone_would_have_lost_it —— 关掉记忆后 同一名字在第 100 轮消失，证明上面那条测的确实是长程记忆的功劳。
  • 前端：npx tsc --noEmit 无错误。
  • 真实 API 冒烟：抽取 prompt 对「我老伴桂芬走了三年了，她生前最爱听黄梅戏」 返回结构正确的 JSON；对纯闲聊句「嗯，今天天气还行」返回三个空数组， 说明「宁可少记，不能记错」的约束确实生效。

尚未做的验证

没有跑过真实的长时端到端对话（需要真人对着麦克风说 20 分钟以上）。 ASR 断线重连的路径是按 SDK 回调语义实现的，但没有在真实断网条件下验证过—— 这是目前最需要实机确认的一处。

8. 已确认的决定

问题结论
危机轮次的历史处理（4.1） 采纳该折中：保留在对话历史中，但不写入长程记忆。
台账的存储与保留 当前明文 JSON、永久保留，可接受。未来迁移到数据库并加密存储。
elder_id 的来源 当前 localStorage 方案可接受。应用未来部署为手机 App， 打开即是老人本人使用，属单用户场景，不需要「选择老人」的界面。
收束等待时间（5.2） 已修复：改为等语音真正播完（详见 5.2 与 6.2）。

9. 实机测试后的修复（第二轮）

真人对着 App 聊过之后暴露出四个问题，其中两个是本次改造自己引入的。

9.1 AI 提到了老人从没说过的人和事 严重

排查过程先排除了两个嫌疑：台账里只有一个没有任何 notes 的名字，不足以支撑编造； 策略库里所有带引号的内容都是提问和通用说法，没有一条断言老人的生活事实。

真凶是事实红线自己的举例。那段文字的用意恰恰是禁止编造，但它写成了：

- 好的回应（只回应已说内容，不新增事实）："五十年的邻居情分，搬都搬不走啊。"
- 好的回应（自然引用记着的事）："你早先说过你俩是五十年的老邻居了。"

四条示例里塞满具体的人和事（老王、五十年邻居、往医院跑），其中两条还标着 「好的回应」。模型手上没素材时就把这些当可用材料说了出来——典型的 few-shot 内容泄漏。其中第二条是本次改造新加的，它更毒：教会了模型 「你早先说过 X」这个凭空断言老人说过某事的句式。

修复：给举例加前提锚点 + 大声声明「这是另外一段对话，一个字都不许搬进你的回复」； 删掉「你早先说过……」那条；新增「开口前的自查」——句中出现任何具体人名/地点/ 时间/数字/事件，先自问来源，两样都不是就删掉。

同时堵上了第二条泄漏通道：台账定了「只从老人原话抽取」的铁律， 但摘要那条漏了——_summarize_input 原本把 AI 的回复也喂给摘要模型， AI 编的话会被摘要吸收成「聊过的事」，之后每轮作为事实注入，幻觉就这么洗白成记忆。 现在只传老人自己的话。

9.2 标点自适应窗口是错的 自己引入

为解决「一句话被切成两三句」，第一版按尾部标点自适应合并窗口：以句号结尾就 只等 350ms。实机转写给出了反证——「上面写的名字。叫王翠芬。」， 句号出现在一句连贯话的中间。

原因：ASR 的标点是按韵律停顿插的，不是语义终止信号。老人边想边说， 思考的停顿会被插成句号。于是这条规则恰好在他话说到一半停顿时判定说完了， 反而更容易切断——启发式在老年人语音上是反向工作的。

修复：去掉标点判断，改单一窗口（默认 1400ms），云端 VAD 从 1500 降到 1000ms （让云端放开切，轮次边界由我们这层定）。唯一可靠的信号是「他又开口了」。

9.3 句间卡顿 自己引入

Stage 1 做首句 TTS 流水线时，playOnce 取完音频后 await 到播放结束 才返回，而 processQueue 又 await 它才取下一句。于是下一句的合成延迟 （网络往返 + CosyVoice 会话启动，300~800ms）被原样暴露成句间空白—— 等于把「开头一次长静默」换成了「中间好几次短卡顿」。

修复：把取音频与播音频解耦，取完立即返回、下一句请求马上发出， 排期交给 nextStartTimeRef，WebAudio 自己把前后两段无缝接起来。 配套把打断用的「已播出多少」从「累计字符串 + 当前段」改成播放时间线数组， 因为多段现在是预排期的，原来的顺序假设不成立了。

9.4 一轮发言产生两条回复

与 9.2 独立的 bug：第二段发言到达时第一条回复还在生成，系统没有作废它， 两条并行跑完都显示出来，内容大半重复。

修复：新一轮用户发言到达时，若上一条回复仍在生成或播放，就地作废—— 中止 SSE、停 TTS、屏幕上那半条按实际说出口的截断（一字未出就整条撤掉）， 并等后端历史截断完成再发下一轮请求（否则新用户消息先进历史， 截断会找不到目标）。复用了打断功能已有的零件。

这两个修复是互补的，但 9.4 才是硬保证：合并窗口再怎么调都可能漏， 而作废机制保证无论切成几段，最终只有一条回复，且它拿到的是完整的话。

9.5 语音打断（barge-in）

TTS 播放期间麦克风帧此前被整个丢弃（防止 AI 自己的声音被转写成用户输入、 形成自问自答的死循环）。现在改为：仍不发往云端，但本地做能量检测—— 浏览器 AEC 已把喇叭声消掉大半，这时出现持续高能量大概率是有人在说话。

三重防误触发：自适应阈值（开头 300ms 测房间本底，阈值 = 本底 × 3.5，另有绝对下限）、 起始 500ms 保护期（防上一句尾音）、连续 3 帧才算（滤咳嗽/关门/电视爆音）。 另有约 770ms 预缓冲，打断成立时先补发，否则老人开口的头几个字会被检测耗掉。

调参集中在 mobile/constants/BargeIn.ts，带 ENABLED 总开关。 阈值必须在真实房间里调——养老院有电视和走廊动静，误触发导致 AI 动不动把话说到一半停掉，比不能打断更糟。

10. 危机轮编人（第三轮实机测试）

10.1 危机轮回了「叫你女儿来」「护工小陈」，两个人都不存在 严重

实机对话里 AI 在危机轮回复：「咱们一起打个电话，叫你女儿来陪陪你，好不好？ 或者，我帮你把护工小陈叫过来，就现在？」老人的回应是：我从没说过我有个女儿， 也没说过护工小陈，我可能就是居家养老。

查证：data/profiles/ 里该老人只有三个字段有值（称呼=王爷爷、听力=好、 慢病=心脏病），emergency_contact / location / room_number 全是 unknown；data/memory/ 里搜 「女儿|护工|儿子|家属」零命中。两个人连同名字都是凭空生成的。

这是 9.1 那一类问题的危机路径变种，而 9.1 的修复没有覆盖到这里。 两处成因叠加：

  • CRISIS_SYSTEM_PROMPT 硬性要求「最后建议联系家人或护工，给个 具体的下一步」——直接点名了两种关系，还要求说具体的；
  • build_crisis_prompt() 是零参数签名。常规路径注入了 memory / profile / summary，唯独危机路径一个事实都拿不到， 9.1 加的那整段事实红线也只在 NORMAL_SYSTEM_PROMPT 里。

被要求说具体的，手上又无事可依，编是必然结果而不是偶发。而危机轮恰恰是最不能 编的一轮：这一轮的全部目的是让他相信有人在听，编出来的「你女儿」一旦对不上， 证明的正好是反面。

修复：

  1. build_crisis_prompt(profile_context, emergency_contact) —— 注入画像， 并把事实红线补进危机 prompt（此前只有常规路径有）。
  2. 「建议联系家人或护工，给个具体的下一步」改成条件式 （build_crisis_contact_block()）：
    · 知道联系人 → 只说记录里的那一个人，不许换称呼；
    · 不知道 → 不许说出任何具体的人，只能反过来问他，让他自己说出 那个人是谁：「你身边现在有人陪你吗？我叫人给你打个电话好不好？」他说出谁就 顺着谁接下去。
  3. CRISIS_VIGILANCE_SECTION 里同样的一句「轻轻带一句身边有人可以陪他 （家里人或者护工）」改成问句，不再替他指定关系。
  4. emergency_contact 是 EXTERNAL 字段，不在 render_profile() 渲染范围内，所以新增 render_emergency_contact() / ProfileService.get_emergency_contact() 单独读一次。
  5. 危机告警事件补上 elder_id。AI 不知道联系人时不许编，兜底就落在 这条告警上——而原来的事件只有 session_id，管理端拿到一个查不到人 的会话号，根本联系不上老人。

另外刻意禁止 AI 向老人承诺「我已经通知谁了」：告警只保证事件被写出去， 不保证有人到场；承诺了没兑现比没说更伤人。

回归锁在 selftest/test_crisis_prompt.py（12 条）。

10.2 顺带暴露的：整套 schema 默认了机构场景

老人那句「我可能就是居家养老」指出了一个没被验证过的前提—— room_number、「护工」这些默认系统跑在养老院里。location 字段是存在的，但标为 EXTERNAL（本期只占位、不会通过对话采集）， 所以它永远是空的，而 prompt 已经按机构场景在写话了。

本次只在危机路径上按「不知道就不说」处理，没有改 schema。真要支持居家场景， location 需要有实际的录入或采集途径，否则这个假设会在别处再冒出来。

11. 事实红线自己的两个漏洞（第四轮实机测试）

11.1 编造从「陈述句」转移到了「问句尾巴上」 严重

老人说「今天早晨还没吃饭呢」，AI 回：「……要不要我陪你煮碗热乎的面？就放点青菜， 再卧个蛋——像小时候小华来串门，你妈总这么给他做。」

查证：小华确实在台账里（小伙伴、已故、「经常一起玩」）。但「来串门」 「你妈」「总这么给他做」台账里一个字都没有。

关键区别：这一轮走的是常规路径，9.1 加的那整段事实红线是在场的，没拦住。 所以问题不在"某条路径漏了红线"（那是 10.1），而在红线本身。两个洞：

  1. 疑问句漏洞。红线原文把规则写成「陈述句只能复述……只能用提问的方式 邀请对方自己讲……提问可以带猜测语气，陈述句不行」。判断标准被写成了 句式。模型于是照做了——把编的内容挂在「要不要我……？」这个问句 的尾巴上、破折号后面带出来。形式上是问句，内容上是断言。规则被满足了， 幻觉照样出去了。
  2. 自查是实体级，不是命题级。原文让它自查「人名、称呼、地点、时间、 数字或事件」的来源。「小华」一查，确实在台账里 → 放行。而"来串门" "你妈煮面"既不是人名也不是数字，压根不触发自查。 台账里有这个人，被当成了台账里有这件事。 台账 notes 又都是「经常一起玩」这种三五个字的碎片，留白极大，模型顺手就补满了。

修复（NORMAL_SYSTEM_PROMPT 与危机 prompt 的事实红线同步改）：

  • 判断标准从"句式"改成"这句话有没有断言一件事"，并写死 「问句不是免罪符」——挂在「要不要……？」后面、破折号后面补的 半句，和独立陈述句是一回事。
  • 自查从过名字改成逐条过说法（谁、做过什么、什么时候、什么样子）， 并写死「台账里有这个人 ≠ 台账里有这件事」「台账那几条短记录， 写着什么就只有什么，没写的部分不是留给你补的」。
  • 把现场翻车那一句作为反面例子写进举例区——抽象规则已经证明拦不住。 例子里的名字换成了虚构的老王，沿用 9.1 那个「这是另外一段对话， 一个字都不许搬进来」的警告外壳；直接把真实的「小华」写进 prompt 会重演 9.1 的 few-shot 内容泄漏。

回归锁在 selftest/test_fact_guardrail.py（6 条），其中一条专门断言 反面例子必须带「不好」标记，防止它自己变成 few-shot 素材。

11.2 AI 提出了它根本做不到的事 严重

同一句里的另一处：「要不要我陪你煮碗热乎的面？就放点青菜，再卧个蛋」 ——蘅小年是个语音陪伴程序，它不能煮面、不能到场、不能递任何东西。

查证结果：四个 prompt（normal / crisis / closing / proactive）里没有任何一处 说明它的能力边界——没有一句话告诉模型它做不了物理动作，所以这类越界完全 不受约束。10.1 修掉的「我帮你把护工小陈叫过来」是同一类问题的另一半：那次修的是 编出不存在的人，这次修的是编出做不到的动作。

系统真正能做的动作只有两个：写危机/求助告警给管理端（_write_event）， 和在设定时间主动开口（proactive）。除此之外一律做不到。

修复方式（已确认）：不禁止一切提议，改主语。提议他自己动一动 （行为激活）临床上对食欲下降和抑郁是有效的，值得保留；不能保留的是"AI 去做"。 新增 CAPABILITY_SECTION，normal 与 proactive 两条路径共用一份 （避免两边各写一版后漂移，与 CRISIS_KEYWORDS 的做法一致）：

  • 「你是个陪他说话的声音，做不了任何实际的事」+ 正反例 （不好：「要不要我陪你煮碗面？」／好：「要不要去厨房下碗热汤面？」）；
  • 提议只能是提议、不能是催，他说不想就顺着，别劝第二遍。

附带堵上的门槛（本次自行加的）：「提议他自己去做」这个方向有个 前提没人验证过——他站不站得起来。mobility 字段 （「腿脚方便不方便」）是 ASKABLE，但目前默认是空的。对一个起不来的人说 「要不要去厨房下碗面」，比什么都不说伤人得多。所以 CAPABILITY_SECTION 里写死：画像里没写腿脚，就不许提任何需要走动的事（下厨、出门、 下楼），这时只说话、不提事。

回归锁在 selftest/test_capability_boundary.py（6 条）。

12. 定时主动招呼开的是一个聋麦（第五轮实机测试）

12.1 招呼说完之后就再也听不见了 严重

现象：AI 主动开口之后，波形照抖，一个字的转录都没有。

不是"听不清"，是每一帧都被前端主动丢掉了。 useASR 的回声消除是个全局互斥标志：TTS 一开始播就把 isTTSMutedRef 置真，置真期间 onaudioprocess 直接 return 不发帧。而 analyser 挂在这个判断的前面，所以波形照抖 ——波形抖动只证明采集在跑，不证明数据在发。

根因在开麦的时机：定时招呼那条路径写的是 await fetchProactive(...) 之后立刻 start()。但 fetchProactive 返回只代表 SSE 文字流结束了，不代表 语音放完了——这个区别在 doEndSession 的注释里早就写明白过 （「fetchClosing 返回只代表文字流完了，语音通常还在后台排队播」）， 但主动招呼这条路径没照做。一段 60 字的招呼，LLM 三秒吐完，CosyVoice 要放 十三到十五秒。于是：

  • t≈3s 开麦，但静音标志还是真 → 帧全丢。后端是「收到第一帧才 create_session()」，所以云端 ASR 会话根本没被创建过；
  • t≈15s 语音放完，tts-end + 200ms 才解除静音；
  • t=23s 无人应答计时器到点 → stopASR()、清屏、 上报 answered=false。

真正能听见的窗口只剩 ≈7 秒，还要在里面说完整句 + 云端 VAD 出 final + 熬过 1400ms 的合并窗口。老人反应慢两秒就彻底没戏，连吃两次就触发 PROACTIVE_NO_ANSWER_GIVEUP，当天不再开口。

修复：新增 waitForPlaybackIdle()，轮询 ttsPlayingRef 等语音真正放完，再多等 TTS_UNMUTE_DELAY_MS（+100ms 余量）让 useASR 恢复收音，然后才 start()。无人应答倒计时也跟着挪到这一刻起算——从文字流结束起算的话， 二十秒里有十几秒耗在放语音上。

顺带堵上的两处（都是这次改动自己带出来的）：

  • 等待期间老人自己按了按钮。窗口从 3 秒拉长到十几秒之后这变得 很可能——AI 刚跟他打完招呼，他伸手去按是最自然的反应。再 start() 一次会把那条 WebSocket 和 MediaStream 直接冲掉（useASR.start 不做自检），旧连接的 onclose 随后又会把新会话一起停掉。 加了 isRecordingRef（isRecording 的 ref 镜像， 闭包里的 state 是陈旧的）在开麦前再查一次。
  • 等待超时。TTS 请求挂死时 isPlayingRef 永远不会翻回来， 不能无限等。waitForPlaybackIdle 返回 false 表示超时，此时静音 永远解不开，开麦只会再得到一个聋子——直接放弃这一轮。不上报无应答： 这次是我们自己的链路坏了，不该算在老人头上去累加放弃计数。

200ms 那个数搬了家。原来写死在 useASR 里，现在两处要用 同一个值（解除静音的延时 / 开麦前要等多久），提到 constants/TTS.ts 的 TTS_UNMUTE_DELAY_MS， 各写一个字面量迟早会对不上。

12.2 顺带查清、但没有改的两处

  • 会话内的沉默唤起不受影响。那条路径麦克风本来就开着、后端会话 已建、ASR_CLOUD_HEARTBEAT=True 保着连接，播完解除静音就恢复了。 TTS 期间听不见是设计如此（防自问自答），不是缺陷。坏的只有定时招呼 这一条——因为只有它自己开麦。
  • 打断检测的底噪基线在这条路径下是坏的，但修完 12.1 之后它够不着了。 resetBargeInState() 是在 tts-start 时调的，那时麦克风 还没开，BASELINE_MS 那 300ms 一个样本都采不到，阈值退化成写死的 MIN_THRESHOLD_RMS = 0.02，完全没有自适应。原本指望它把静音期里 开口的老人捞回来，实际捞不住（安静房间里轻声说话过不了 0.02）。 12.1 修完之后 start() 的两个调用点都保证麦克风开的时候不在静音态 （toggleConversation 先调 stopTTS()，定时招呼等到播完）， 这个退化路径已经不可达——所以没有为它加防御代码。 但它是个真实存在的陷阱：以后再加任何「TTS 播放期间开麦」的路径， 基线必须重采，否则打断会静默失灵。

13. 编造感知 + 时间全丢（第六轮实机测试）

13.1 它描述了它看不见的东西 严重

现场（主动招呼）：「刚才您望着门口那会儿，我瞧见窗台上的光挪了半寸」 「今儿风软」。蘅小年只有麦克风——看不见他、看不见窗台、没有天气数据。

这是 §10.1（编出不存在的人）、§11.2（编出做不到的动作）之后的第三块： 编出感知不到的观察。CAPABILITY_SECTION 管的是"做不了的动作"， 一个字都没管"感知不到的东西"。

更糟的是prompt 自己教的：主动开口硬规则第 3 条原文写着 「什么都没记着，就说点眼前的（天气、时候）」——「今儿风软」 就是这句直接教出来的。

修复：CAPABILITY_SECTION 新增「你能感知到什么、 感知不到什么」一节，配正反例（不好：「我瞧见窗台上的光」；好：「刚才安静了一会儿」 ——静默是它真测得到的）。硬规则第 3 条删掉「天气」，保留「时候」 ——因为 13.2 把当前时间真的给了它，时候从此是它知道的事。

已确认的外溢：CAPABILITY_SECTION 是 normal 与 proactive 共用的一份，所以感知边界同时约束了普通对话轮。这是有意的—— normal 路径同样不该说「我看您脸色不好」。

另加硬规则第 4 条：提以前的事必须说清那是以前的（「上回您说」）， 不许写成此刻正在发生的景象。这治的是「像小时候小华他们跑过墙根，影子一跳一跳的」 ——把台账里的回忆焊到当下，制造出一种它并不在场的亲密感。

13.2 今天以前的事，全被当成刚刚发生 严重

时间信息在三层上全丢了：对话历史条目只有 {role, content}；台账存了 last_mentioned 但 render_ledger 渲染时整个扔掉；四个 prompt 没有一处说今天是几号。

实盘台账里的现成证据：

小华 [已故]：…老人今天才知道小华去世了     last_mentioned: 2026-08-13

这条 note 的文本里写着「今天」，是 8 月 13 日写下的。模型每天 读到的都是「今天」——小华于是连着好几天都是今天死的。所以这不只是 渲染层缺日期：相对时间词已经被固化进存储内容本身，光加日期前缀救不回旧条目。

修复分三处：

  • build_now_block()：注入 normal / crisis / closing / proactive 四个 prompt。钟点走 12 小时制——这段话是要被念出来的，没人讲「下午13点」。
  • render_ledger：每条加 〔8月13日〕 前缀（数据本来就有）， 跨年的条目补年份。同时在台账块开头加一句兑冲说明： 「条目内容里出现的『今天』指的是记下它的那一天，不是现在」。 这句是关键——光加前缀模型不会自己去做这个换算，旧条目已经 写死改不动了，只能靠这句兜住。
  • EXTRACT_SYSTEM_PROMPT：禁止 note 里再出现「今天/昨天/刚才/最近」 这类词。堵住新数据继续被同样的方式污染。老人自己说的绝对说法 （「走了三年了」）可以留——那是他的话，不是抽取模块添的。

已确认：旧台账不清洗，靠日期前缀 + 兑冲说明兑。

回归锁在 selftest/test_time_labels.py（10 条）与 test_capability_boundary.py 新增的 4 条，全部离线可跑。

13.3 查清了但没有改的

  • 采集本来就接进主动开口了。一开始以为"按缺失字段主动了解" 这套没做，查下来 plan_elicitation 在主动开口路径里是被调用的 （llm_service.py）。那两段失真的招呼都是 silence 触发， 而 silence 走的是会话内类别（当时是 grief），_SAFE_CATEGORIES 只放 neutral/positive 过——所以采集被故意抑制了。哀伤叙事中途开新话题 就是打断，这条抑制有临床理由，已确认不动。
  • 台账在按字面串去重，同一个人裂成多条。实盘里 小华／小黄（后者几乎肯定是 ASR 把"小华"转错）、王叔叔／王爷爷、 老伴／老伴儿，三组六条其实是三个人。_merge_person 用 name 精确 匹配，转写差一个字就新建条目。是真问题，不在本轮范围。
  • 会话内对话历史仍然没有时间戳。单次会话里各轮相隔几分钟， 加了是噪音；真正出事的是跨会话的台账，已由 13.2 覆盖。

14. 「我自己」：老人自己看、自己改的画像页

14.1 范围：只开放 13 个 askable 字段 已确认

底部第二栏「玩游戏」改成「练练脑」（two.tsx 至今还是 Expo 脚手架 原样，所以这一步只是改标签和图标），右边新增第三栏「我自己」。

画像一共 22 个字段，这一页只列 13 个 askable：

  • 不列 external（紧急联系人 / 药名 / 房间号）——设计上就是护理员 录的，AI 不问。这一页在老人随手能点到的底部栏里，不该同时装着这些。
  • 不列 observable（话多话少 / 情绪底色 / 能聊多久）——系统从对话 行为统计出来的，给个能改的入口，下一轮 observe_behavior 就把 老人改的值盖掉了，等于骗他白改一次。

门槛写在 ProfileService.set_slot_manually 里（is_askable 一关挡掉其余九个），不在路由层——路由只做搬运。

14.2 两处没写进需求、但必须有的

（一）清空。实盘画像里 address 的值是 「我」——从 AI 自己那句「我该怎么称呼你呀？」里抽错的 （evidence 字段留着原句，一看就知道）。一个改不掉错值的编辑页没有意义。 所以 set_slot_manually 收空串表示清掉：回到 unknown， needs_attention 重新为真，AI 以后会再问一次——等于把这一栏交还给 对话去采。

清的时候 evidence / source / confidence 一起清。只清 value 会 留下旧依据，下一次抽取拿它当上下文，等于没清干净。

（二）岁数的输入。set_birth_year 只收四位年份， 并且明确拒绝年龄（「存年龄一年后就是错的，而且没有任何机制会发现它错了」）。 但这一栏对老人显示的标签是「岁数」，他一定会输 83，然后被静默拒绝。

处理方式是在写入口加 _year_from_age_or_year()： 1900~今年 当年份，40~120 当岁数换算成出生年，两个区间不 重叠所以没有歧义，都不像就原样交给 set_birth_year 去拒。 schema 一个字没动——存的仍然只有四位年份，年龄照旧由 compute_age() 每次读时算。

14.3 前端的三条取舍

  • 一行一个字段，行高 ≥72。手抖也点得中。
  • 没填的写「还没说」，不留白。留白在老人眼里像是坏了。
  • 编辑用整屏浮层，不做行内输入框。行内框在小屏上会被弹出的 键盘顶掉，老人看不见自己正在改哪一栏。

被拒的写入（目前只有岁数）不会把人关在浮层里干等——直接说「这个岁数看着 不太对，您再看看？」，留在原地让他改。

14.4 撞上的一处：getElderId() 中途变成异步了

写这一页的时候 constants/Session.ts 的 getElderId() 已经 从同步改成 async（原生端改走 AsyncStorage，否则打包后每次冷启动都退到 FALLBACK_ELDER_ID，多台设备共享同一份记忆）。tsc 当场抓到了。

照 useLLM 已有的做法处理：惰性 ref 缓存 Promise 本身， 不缓存 resolve 后的值——不管哪个调用先发起请求，都等同一次读取结果， 不会在 AsyncStorage 还没返回时就把默认值发出去。

14.5 验证

前端只有 tsc --noEmit（mobile/ 至今没有 JS 测试框架）， 页面本身需要实机点一遍。

16. Docker 部署与 APK 打包（2026-08-18）

16.1 后端 requirements.txt 里的 CPU torch 索引不生效

torch --index-url https://download.pytorch.org/whl/cpu 这种写法看着像是 「给这一行单独指定索引」，但 pip 不支持这种逐行语法——--index-url 只在 整份 requirements 文件级别生效，写在某个包后面会被静默忽略。本机 Windows venv 之所以 装出了 CPU 版，是因为默认 PyPI 索引上 Windows 平台恰好没有匹配的 CUDA wheel，纯属巧合； Linux 镜像里同样的命令会连一整套 CUDA 运行时（cudnn/nccl/cusparselt/cublas 等，实测 约 3~4G）一起装进去，且这台机器根本没 GPU。

没有改 requirements.txt——本机现有 venv 靠这份文件"能用"， 不想动它引入不必要的风险。改在 backend/Dockerfile 里：分两条 RUN， 先显式按 CPU 索引装 torch/torchaudio，再装其余依赖； requirements.txt 里那两行版本已满足会被直接跳过，不会被换成 CUDA 版。

16.2 模型缓存和运行时数据不进镜像

.model_cache/（~3.9G）、data/（记忆台账、画像、危机事件， 含真实老人信息）、.env（API 密钥）三者都不 COPY 进镜像 （见 backend/.dockerignore），理由不同但结论一致：

  • 模型缓存——纯粹是体积问题，镜像升级不该每次带着 3.9G 权重走一遍网络； docker-compose.yml 里挂载成 volume，服务器上只需传一次。
  • 运行时数据——和 .gitignore 里 backend/data/ 不入库的 考虑一致（见第 10 节前后），不能把真实用户数据焊进一份可能被到处分发的镜像里。
  • .env——密钥不该躺在镜像 layer 里被 docker history 之类的命令翻出来， 运行时用 --env-file 注入。

16.3 Android 明文流量：usesCleartextTraffic

服务器暂时没上 TLS，是 http://47.253.82.38:8050。Android 9（API 28）起 系统默认拒绝 App 发起的明文网络请求，不处理的话 APK 装上之后连不上后端，且报错 信息（一般是 CLEARTEXT communication not permitted）不会直接告诉你原因， 容易当成后端没起来去排查。

用 expo-build-properties 插件在 app.json 里开 android.usesCleartextTraffic: true。这是全局开关，不限定域名——够用于 现阶段测试，但意味着这个 APK 对任意域名的明文请求都不拦截。真要发正式版应该给 服务器配反向代理挂证书，改回 https://，再关掉这个开关。

16.4 前端服务器地址从 6 处硬编码收成 1 处

http://localhost:8050 原来散在 index.tsx（3 处）、 profile.tsx、useLLM.ts、useASR.ts、TTS.ts 六个文件里，换服务器地址得挨个改，容易漏。新增 constants/Api.ts 作为唯一 来源（API_BASE_URL / WS_BASE_URL），其余六处全部改成引用它。 之后换地址（比如后端换机器、上了域名/TLS）只改这一个文件，重新走一遍 EAS 打包。

地址是编译时打进 APK 的，不是运行时读的——改完 Api.ts 必须重新 eas build、重新装到手机上才会生效，这点在 mobile/DEPLOY.md 里专门提了一句，容易被忽略。

16.5 APK 用 EAS Build 的 preview profile，不是默认 profile

EAS 默认产出 .aab（Google Play 用的格式），手机装不了。 eas.json 里新增 preview profile，显式 "android": {"buildType": "apk"}，才会出可以直接装的 .apk。

app.json 之前没有 android.package——EAS 构建必须有包名， 补了 com.agetalker.mobile。name/slug 没动， 不在这次改动范围内。

16.6 部署三份文档

backend/DEPLOY.md（本机 build → save → scp → 服务器 load/compose up， 含模型缓存怎么弄过去两个方案）、mobile/DEPLOY.md（EAS 打包步骤 + 明文流量 的说明）、以及本节。backend/.env.example 补了个空模板（只列变量名， 不含真实值），方便服务器上手写 .env 时对着抄。

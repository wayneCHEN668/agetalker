# 练练脑：年代主题翻牌配对游戏 — 设计文档

- 日期：2026-08-18
- 状态：设计已确认，待写实现计划
- 影响范围：`mobile/` 前端，不涉及后端

---

## 1. 背景

`app/(tabs)/two.tsx` 至今是 Expo 默认模板（`Tab Two` + `EditScreenInfo`），一个字没动。
但 tab 本身已经配好：`app/(tabs)/_layout.tsx` 里标题「练练脑」、图标 🧠 都在位。
需求是把这个空壳做成一个帮助老年人锻炼记忆力的简单游戏。

## 2. 核心矛盾及其解法

### 2.1 矛盾

本项目的对话 prompt **明令禁止记忆考核**：

- `backend/prompts/templates.py:214` — 孤独类别红线第一条：「严禁记忆考核（绝不问"您还记得吗"）」
- `backend/prompts/templates.py:1079` — 主动开口硬规则第 5 条：「不要问"你还记得吗"」

这两条有临床依据：对正在经历认知衰退的老人，「考他记不记得」这件事本身就在反复
确认他的衰退。他答不上来的那一刻，伤害比不玩这个游戏大得多。

因此「记忆力游戏」这个需求与 app 已建立的价值观存在张力。不先解掉，做出来的东西
会人格分裂——左边 AI 温柔地绝不考他，右边游戏上来就问「还记得这是什么吗」。

### 2.2 解法：翻牌配对 + 年代卡面皮肤

**翻牌配对的游戏机制天然绕开整个红线问题。**

它考的是「刚才那张牌在哪」（短期工作记忆），**不是**「你知不知道这是什么」
（知识考核），也**不是**「你记不记得自己的人生」（自传考核）。

年代元素只作为**卡面皮肤**——牌面画收音机、算盘、座钟——提供亲切感和潜在
话头，但游戏本身一个字都不问它是什么。答不上来这件事在这个机制里根本不存在。

附带解掉两个实施风险：

- **零版权问题**：用矢量图标，不碰老歌音频、老照片、老电影剧照
- **零 LLM 编造风险**：不需要模型生成任何事实，而本项目已为「模型编事实」写了大量红线

## 3. 已确认的设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 内容方向 | 年代公共记忆（非老人自己的记忆） | 答不上来不丢人；避开记忆考核红线；新用户第一天就能玩 |
| 游戏形式 | 翻牌配对 | 只考短期记忆，不考知识不考人生（见 §2.2） |
| 难度 | 老人自选三档，文案「牌少一点 / 正好 / 牌多一点」 | 避开「简单/困难」的自我能力评估；不用自适应，因为牌悄悄变少被察觉后「机器觉得我不行了」比挫败本身更伤人 |
| 卡面素材 | `@expo/vector-icons` 图标 + 中文词 | 已在依赖里，零新依赖零版权；图形+文字双通道对视力差的老人更友好 |
| 反馈 | 无计时、无分数、无「错误」提示、无失败态 | 这个用户群没有讨论空间 |

### 3.1 被砍掉的（v1 范围外）

**读画像个性化选材**（用 `birth_year` / `hometown` / `occupation` 筛卡面）。

砍掉的理由：年代方向的价值来自「卡面是老物件而不是抽象图形」，这个价值不依赖读画像。
而按出生年份筛选实际区分度很弱——1940 年生和 1955 年生的人都认得收音机、算盘、
缝纫机——却要付出一次 API 调用、加载态、失败降级的代价，还让游戏在后端挂掉时不能玩。

**配对成功后把话头递给聊天 tab**（比如「这搪瓷缸子你使过吧」+ 一键跳转）。

这个想法方向是对的，是本 app 独有的价值，但它要改动 `app/(tabs)/index.tsx`
（25KB 的复杂文件）并引入跨 tab 通信机制。留作 v2。

## 4. 范围

**做**：一个纯前端、自包含的年代主题翻牌配对游戏。不碰后端，不碰聊天 tab，断网可玩。

**不做**：见 §3.1。

## 5. 文件结构

```
app/(tabs)/two.tsx              屏幕组装，不含游戏逻辑
components/game/
  MemoryCard.tsx                单张牌：翻转动画、大点击区
  CardGrid.tsx                  网格，按档位定列数
  DeckSizePicker.tsx            「牌少一点 / 正好 / 牌多一点」
  RoundComplete.tsx             收尾 + 再来一局
constants/MemoryGame.ts         素材库、档位、布局常量
hooks/useMemoryGame.ts          游戏状态机（纯逻辑，零 RN 依赖）
```

### 5.1 关键约束

`hooks/useMemoryGame.ts` **不得 import 任何 React Native 组件**，只是状态 + reducer。

这样游戏规则可以被单元测试，UI 只是它的投影。这与项目现有的
`useASR` / `useLLM` / `useTTS` 模式一致。

## 6. 状态机规格

```
（进入屏幕，读 AsyncStorage 档位，直接发牌）
        │
        v
     playing ──全部配对──> complete ──再来一局──> playing
        ^                                            │
        └──────────── 换档位（随时）─────────────────┘
```

**没有 `idle` / 选档位的前置界面。** 老人每次进来先做一道选择题是额外的认知负担，
所以直接发牌开局，档位用上次记住的（首次为「正好」）。档位选择器常驻屏幕下方，
想换的时候才碰——换档位等同于用新牌数重开一局。

### 6.1 playing 内部的转移

| 事件 | 行为 |
|---|---|
| 翻开第 1 张 | 记录为 firstFlipped，保持正面朝上 |
| 翻开第 2 张，图案相同 | 两张标记 matched，**永久留在场上正面朝上** |
| 翻开第 2 张，图案不同 | **停留 1200ms** 后两张一起翻回背面 |
| 判定期间（1200ms 窗口内）的任何点击 | **忽略** |
| 点击已 matched 的牌 | 忽略 |
| 点击当前已翻开的第 1 张 | 忽略（不允许「取消」，避免误操作导致的困惑） |

### 6.2 三个细节的理由

- **1200ms 停留**：老人反应慢，翻回太快他还没看清第二张牌就消失了，这一轮的信息
  等于白给。此值需现场调整，应作为 `constants/MemoryGame.ts` 里的具名常量而非魔数。
- **判定期锁定**：手抖连点会把状态机搞乱（第三张牌翻开时 firstFlipped 已被覆盖）。
- **配对成功的牌不移除**：移除会导致布局跳动，老人会丢失赖以定位的空间记忆锚点。

### 6.3 完成条件

所有牌均为 matched 时进入 `complete`。

## 7. 档位与布局

| 档位文案 | 牌数 | 对数 | 网格 |
|---|---|---|---|
| 牌少一点 | 6 | 3 | 2×3 |
| 正好（默认） | 12 | 6 | 3×4 |
| 牌多一点 | 16 | 8 | 4×4 |

- 文案刻意避开「简单 / 困难」——不逼老人对自己的能力做评估。
- 选择持久化到 `AsyncStorage`（`@react-native-async-storage/async-storage` 已在依赖里），
  下次进入屏幕时直接用它发牌，不再询问（见 §6）。
- 首次使用（AsyncStorage 无值）默认「正好」12 张。
- 档位选择器**常驻屏幕下方**，不是前置的 gate 界面。中途换档位 = 用新牌数重开一局，
  当前进度作废（这是可接受的：这个游戏没有「进度」的价值，随时重开无成本）。

## 8. 卡面素材库

`constants/MemoryGame.ts` 导出一组老物件条目。**下限 8 个**（16 张的大档需要 8 对），
**目标 16 个**（留出随机性，避免每局都是同一批牌）：

```ts
type CardFace = {
  id: string;      // 稳定标识，用于配对判定
  icon: string;    // MaterialCommunityIcons 图标名
  zh: string;      // 中文词，显示在图标下方
};
```

候选物件（按图标库命中把握度排序，最终以实际可用性为准）：

- **大概率有**：收音机、算盘、茶壶、座钟、蒲扇、钢笔、竹篮、台灯、雨伞、木椅、
  剪刀、钥匙、镜子、梳子
- **需核对**：缝纫机、煤油灯、老式电话、砚台、热水瓶

**实现注意**：图标名需逐个到 `@expo/vector-icons` 的 MaterialCommunityIcons 中核对，
**核对通过的才能进库**——不能写一个猜的图标名，渲染出来会是空白方块。凑不齐 10 个
下限时，用日常物件近似替代 + 中文词兜底（词能补上图标补不了的年代感）。

每局从库中随机抽取 N 对，局内不重复。图标颜色套用 `constants/Design.ts` 色板。

## 9. 反馈与无障碍规格

| 场景 | 表现 |
|---|---|
| 配对成功 | 卡片轻微放大 + 底色转 `Design.colors.primaryContainer` |
| 翻错 | **零负面反馈**。不变红、不震动、不出声，牌就是翻回去 |
| 全部完成 | 一句温暖的话 + 「再来一局」大按钮。**不显示用时、不显示翻牌次数** |

- 点击区 ≥ 64×64 px（远超 44 的通用无障碍标准，因为目标用户手抖）
- 每张牌 `accessibilityLabel` 使用其中文词
- 字号、颜色、圆角全部走 `constants/Design.ts`，不新造设计 token

## 10. 测试策略

### 10.1 现状

前端**目前跑不了任何测试**：`components/__tests__/StyledText-test.js` 是 Expo 模板
遗留，`package.json` 里既无 jest 配置也无 `test` 脚本。

### 10.2 方案

加 `jest-expo` + `test` 脚本，**只测 `useMemoryGame` 这一个纯逻辑 hook，不测 UI 组件**。

必测的五项（写错了肉眼看不出来）：

1. 洗牌结果严格成对——每个 face id 恰好出现 2 次，且总数等于档位牌数
2. 配对判定正确——相同 id 判为 matched，不同 id 不判
3. 判定期锁定生效——1200ms 窗口内的第三次点击被忽略（用 fake timers）
4. 完成条件正确——所有牌 matched 时且仅当此时进入 `complete`
5. 中途换档位——牌重新洗、牌数变为新档位、已 matched 状态全部清空

### 10.3 已知风险

jest + Expo 54 + React 19 的配置可能不顺，有踩坑可能。若配置成本失控，
退路是保持 `useMemoryGame` 的纯逻辑性质，测试留待后补——但纯逻辑这一点
不能因此放弃，那是可测性的前提。

## 11. 开放项

1. **大档卡片尺寸**：大档已从 20 张（4×5）降到 16 张（4×4），正是为了预防
   卡片过小、中文词读不清。16 张下单卡仍约 85px，需真机复核；若文字仍嫌挤，
   退路是大档只留图标、去掉文字（图标本身不缩水）。
2. **1200ms 翻回延迟**：需要真实老人测试后调整。
3. **图标库覆盖度**：真正的中国六七十年代特有物件（粮票、搪瓷缸子、二八大杠）
   图标库里没有，只有自绘 SVG 才能真做出来。v1 接受「通用老物件」的妥协，
   若年代感实测不足，v2 可考虑引入 `react-native-svg` 自绘。

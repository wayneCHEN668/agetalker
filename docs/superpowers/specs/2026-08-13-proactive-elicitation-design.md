# 主动开口引擎 + 画像引导采集 —— 设计文档

日期：2026-08-13
状态：已评审，待实现
适用分支基线：`fix/field-test-issues`

---

## 1. 背景

蘅小年目前是**纯被动**的：只有老人按下按钮、说出一句话，系统才会响应一次。
两个后果：

1. 老人不主动开口，App 就是一块沉默的屏幕。对独居老人和机构里行动不便的
   老人，"要先想起来去用它"本身就是门槛。
2. 关于老人的信息只能**被动捡拾**——[memory_service.py](../../../backend/services/memory_service.py)
   每轮从老人原话里抽 `people / events / preferences` 存进台账，但它只能记
   老人碰巧说出来的东西。老人从没提过的事，系统永远不知道。

本设计解决这两件事，并且让它们互相咬合：**主动开口的时刻，恰恰是采集的最佳
窗口**——那时没有正在进行的叙事需要尊重，AI 起任何话头都不算打断。这是把两个
子系统放进同一份 spec 的实质理由，不是打包方便。

## 2. 目标与非目标

### 目标

- 建立老人的结构化画像，字段可枚举、可判断"填了没有"
- 在不损害陪伴质量的前提下，通过对话自然采集可采集的字段
- 支持两种主动开口：会话内沉默唤起、定时主动招呼
- 保证不重复追问，尊重老人的沉默与拒绝

### 非目标（明确不做，各自单独立项）

| 不做 | 原因 |
|---|---|
| 用药定时提醒 | 安全关键功能，需要确认回路与准确性保证，改变 App 定性。本设计只采集**用药时间**作为画像字段，不承诺提醒 |
| 位置服务（地域匹配、回家路线） | 与对话系统技术上几乎完全解耦，需要的是定位精度与后台权限，不是 LLM |
| 家属录入端 | 全新的角色与界面 |
| 护理员画像视图 | schema 预留 `source` / `confidence` / `evidence` 字段，但本期不做界面 |
| 作息自动学习 | 先用采集到的作息 + 默认时间表；自动学习是后续优化 |

### 一条贯穿全局的约束

**采集来的数据不能直接驱动会发出声音的行为。** 作息字段是 LLM 从口语里抽的，
有确定的出错率；抽错一个数字就可能变成半夜三点自己说话。中间必须有硬边界
（见 6.4 夜间静默窗口）。

## 3. 画像结构

### 3.1 画像与台账是两个东西

不合并。

| | 台账（现有） | 画像（新增） |
|---|---|---|
| 内容 | 自由文本，叙事记忆 | 结构化 slot |
| 增长 | 无限（有 cap 淘汰） | 有限、可枚举 |
| 用途 | "AI 记得你说过什么" | "AI 知道你是谁" + 判断该问什么 |
| 更新 | 合并追加 | 状态机推进 |

合并之后，"这个字段填了没有"就无法判断——而它正是不重复询问的前提。

### 3.2 字段按采集途径分三类

**只有第一类需要"找时机问"。** 这个划分把"何时采集"的问题规模缩小了一半以上。

#### 可问的（askable）—— 对话中引导采集

| slot | 说明 | 半衰期 |
|---|---|---|
| `sensory_hearing` | 听力状况（耳背程度） | 180 天 |
| `sensory_vision` | 视力状况 | 180 天 |
| `chronic_conditions` | 老毛病、慢性病 | 180 天 |
| `medication_times` | 用药时间（**不含剂量**） | 180 天 |
| `sleep` | 睡眠状况 | 90 天 |
| `mobility` | 行动能力（能否自己出门、用不用拐杖轮椅） | 90 天 |
| `daily_routine` | 日常作息（几点起、午睡、几点睡） | 90 天 |
| `hobbies_current` | 现在还在做的爱好 | 180 天 |
| `hobbies_past` | 以前的爱好 | 永不过期 |
| `occupation` | 职业生涯 | 永不过期 |
| `hometown` | 家乡 | 永不过期 |

`medication_times` 只记时间不记剂量：剂量属于医疗信息，靠口语抽取不可靠，
错误代价高。药名与剂量走外部录入。

#### 可观测的（observable）—— 永远不问，从对话行为统计

| slot | 统计方法 | 最小样本 |
|---|---|---|
| `talkativeness` | 老人每轮平均字数 | 20 轮 |
| `interaction_preference` | AI 提问后 vs 陈述后，老人回复长度对比 | 20 轮 |
| `taboo_topics` | 老人岔开话题时记录的 `slot_hint`（`declined` 的副产品） | — |
| `emotional_baseline` | router 产出的 `category` 频次分布 | 30 轮 |
| `attention_span` | 会话平均时长 | 5 次会话 |

问一个老人"您性格怎么样"本来就是荒谬的。而 `emotional_baseline` 所需的数据
**现有系统每轮都在产出**（router 的 `category`），只是从没被统计过。

样本不足时宁可留空：错误的性格判断会一直影响后续所有对话的语气。

#### 外部录入的（external）—— AI 不问

`location`、`medication_names`、`emergency_contact`、`room_number`。

本期只在 schema 里占位，由后续立项的家属端/设备侧填入。

### 3.3 关系网络：派生视图，不重复存储

已故的重要亲人是哀伤类别最关键的上下文（AI 不知道就可能在错误的时刻提起）。
这些信息已经存在于台账的 `people[].status` 里，画像层只做一个**派生视图**
（读时从台账计算），不复制一份存储——两份会漂移。

### 3.4 采集优先级

不随机挑空字段，按"拿到之后能带来什么"排：

1. `sensory_hearing` / `sensory_vision` —— **唯一能闭环改变系统行为的字段**
   （耳背就调慢 TTS 语速、调大音量）。其他字段只让 AI 会说话，这个字段让 App
   变得能用。越早拿到收益越大。
2. `daily_routine` —— 决定定时招呼几点开口，不知道就只能瞎猜。
3. `chronic_conditions` / `medication_times` —— 高频对话素材，也是后续用药
   提醒立项的数据基础。
4. 其余按对话价值排。

## 4. 采集时机

### 4.1 线索检测并进现有路由调用

「顺水推舟」需要每轮判断"老人这句话里有没有露出某个字段的线索"。**不新开
LLM 调用**——路由器每轮本来就在跑，加一个输出字段即可，零额外延迟、零额外成本。

`_ROUTER_OUTPUT_FORMAT`（[templates.py](../../../backend/prompts/templates.py)）
新增一个字段：

```
{
  "category": "...",
  "is_crisis": ...,
  "matched_signals": "...",
  "strategy_id": "...",
  "slot_hint": "露出线索的 slot 名，没有就空字符串"
}
```

这不是随手添加：v3 变更记录里，`strategy_id` 就是以同样的理由并进路由调用的
（"不增加新的网络往返"）。沿用该先例，架构一致。

`slot_hint` 缺失或不是合法 slot 名时，一律当作空——采集是增强能力，宁可不采。

### 4.2 两种采集，两套门槛

**这是本设计能不违和的关键。** 它们不该用同一个判定。

#### 顺水推舟（低门槛）

老人自己提到了线索，AI 顺着多问一句。它**不改变话题**，只是深入老人自己已经
打开的话头。

- 触发：`slot_hint` 非空
- 唯一硬禁止：`is_crisis` 或处于危机警戒期
- **允许在敏感类别下进行**：老人说"最近腰疼得睡不着"，这既是抑郁的躯体化
  信号，也是 `chronic_conditions` / `sleep` 的线索。顺着关心一句完全恰当。

#### 主动起话头（高门槛）

为了填某个空字段而开新话题。必须**全部**满足：

| 条件 | 判断依据 | 理由 |
|---|---|---|
| `category ∈ {neutral, positive}` | router 输出 | 敏感叙事中开新话题就是打断 |
| 不在危机警戒期 | 现有 `_is_crisis_vigilant()` | 危机余波期绝不采集 |
| `phase != 'closing'` | 现有 `get_phase()` | 收尾就该收尾 |
| 未在连续提问 | 现有 `_should_restrain_questions()` | 见下 |
| 距上次采集 >= `ELICIT_COOLDOWN_TURNS` 轮 | 新增冷却计数 | 防止一轮接一轮 |

**第四条必须复用现有节流器，不能另起一套。** 否则策略路由问一句、采集规划器
问一句，两个系统各自觉得自己很克制，老人体验到的是连环追问。这是加第二个
决策系统时最容易漏的坑。

### 4.3 采集强度

- 一次会话**最多 2 条**主动起话头
- 顺水推舟不设上限（它本来就是自然对话的一部分）

理由：一次对话可能只有 10-20 轮，问 5 条就意味着 25% 以上的轮次在采集，老人
一定会察觉到味道变了。

### 4.4 与现有策略路由的关系

采集**不抢** `strategy_id` 的决策权。策略仍然决定这一轮 AI 要做什么；采集只是
在 prompt 里追加一句"顺带关心一下 X"或"可以从 X 起个话头"。冲突时策略优先。

## 5. 不重复询问

### 5.1 为什么布尔值不够

"字段有值 = 问过了"会在四个地方失效，第一个最致命：

1. **问了但老人没答**——岔开话题、含糊过去。字段仍是空的，规划器下次又问，
   再下次又问。老人体验到的是被逼问，系统却自认为"还没采到，该问"。
2. 老人**明确拒绝**。
3. 答得模糊（"还行吧"），算填了还是没填。
4. 信息**会过期**——三年前记的"喜欢下棋"可能早就不下了。

### 5.2 Slot 状态机

```
unknown ──问了/采到线索──> asked ──老人答了──> filled ──半衰期到──> stale
                             │                                      │
                             │                                      └──改用"确认"而非"提问"
                             └──明确拒绝 / ask_count>=2──> declined
                                        （终态，永不再问）
```

**`asked` 必须是独立于 `filled` 的状态。** 这是解决失败模式 1 的唯一办法：
只看有没有值，就永远分不清"从没问过"和"问过但没答上来"。

### 5.3 Slot 数据结构

```json
{
  "value": "腰不好，阴天疼",
  "status": "filled",
  "ask_count": 1,
  "last_asked": "2026-08-13T10:22:31+08:00",
  "last_filled": "2026-08-13T10:22:31+08:00",
  "source": "conversation",
  "confidence": "high",
  "evidence": "老人原话片段"
}
```

- `status`: `unknown | asked | filled | declined | stale`
- `source`: `conversation | observed | external`
- `evidence`: 来源追溯，支撑将来的护理员视图导出（本期不做界面，但字段先带上）

### 5.4 最重要的一条规则：沉默即拒绝

**`ask_count >= 2` 且仍未填上 --> 自动降为 `declined`，永不再问。**

老人两次都岔开话题，那就是不想说，不管他有没有明说出口。

没有这条硬闸，前面所有的"安全窗口""节流"都只是降低频率——一个永远填不上的
字段最终一定会被问到第五次、第十次。这也是对老人的尊重：不是每件事都该被
问出来。

代价是有些字段会永久空着。这是刻意用覆盖率换体验的取舍。

### 5.5 过期不用"问"，用"确认"

`stale` 状态走的是**完全不同的话术**：

- 错误：「您平时有啥爱好」—— 等于把人当陌生人，老人会觉得"你把我忘了"
- 正确：「您那个腰，这阵子还疼不」

**确认已知信息是亲近的表现，重新提问是疏远的表现。** 这一条如果做反了，长期
记忆的价值会被自己抵消掉。

### 5.6 观察类字段没有 asked 状态

只有 `unknown --> filled`，靠统计累积，且需满足 3.2 表中的最小样本量。

## 6. 主动开口引擎

### 6.1 后端接口

新增 `POST /llm/proactive`，参数 `session_id / elder_id / trigger`
（`trigger ∈ {silence, scheduled}`）。

它和现有 [`stream_closing`](../../../backend/services/llm_service.py) 是同一个
形状——没有老人输入、后端自己生成一段话、走同样的 SSE 结构流出去。前端
`fetchClosing` 的消费逻辑几乎可以原样复制。**这条链路已经跑通并实机验证过，
是本设计里风险最低的部分。**

### 6.2 说什么：话头的三个来源

按优先级：

1. **回指**——台账里有值得跟进的事：「上回您说腰疼，这两天好点没」。最有温度，
   而且天然就是 5.5 的 stale 字段"确认"，一举两得。
2. **画像空缺**——安全窗口下，起一个能自然带出空字段的话头。
3. **纯寒暄**——前两个都没有时的兜底。

**硬规则：第一句不能是问句。** 措辞写成「陈述 + 轻轻带一句」，不是直接抛问题。
上来就问就是查户口。这恰好是现有 closing prompt 的镜像（收尾不提问，开场不逼问）。

### 6.3 触发源 1：会话内沉默唤起

老人已开着对话但一段时间没说话（20-30 秒量级，远长于现有
`ASR_SILENCE_FRAMES` 的 1.5 秒断句阈值）。

计时器有两个**必须排除**的区间：

- **TTS 播放期间**（现在 ASR 本来就被静音，见 `useASR` 的回声消除）
- **LLM 生成期间**

否则 AI 会在自己刚说完的瞬间又开口。

### 6.4 触发源 2：定时招呼

时间来自画像的 `daily_routine`，没有就用默认表。到点且当前无进行中会话 -->
自动开会话、AI 先说话、然后自动开麦。

**前提：设备常驻前台**（床头平板/挂墙屏）。这个部署形态假设必须写进文档，
不能默认成立。

三条护栏，都不是功能需求，而是"别让这东西变成扰民设备"：

**(a) 无人应答的收场。** 定时招呼时老人很可能不在。必须有：开麦等待
`PROACTIVE_NO_ANSWER_SEC` 秒无应答 --> 安静收场，不重复呼叫；**当天连续无应答
`PROACTIVE_NO_ANSWER_GIVEUP` 次后，当天不再尝试**。没有这条，设备会变成定时
扰民的喇叭——而且扰的是隔壁床的人。

**(b) 夜间硬静默窗口。** 不管作息表怎么配，`PROACTIVE_QUIET_HOURS`
（默认 21:00-07:00）一律不主动开口。这是防配置错误的兜底，见第 2 节末尾那条
贯穿全局的约束。

**(c) 危机警戒期禁止。** 老人刚经历过危机对话，设备过一会儿自己出声是惊吓，
不是陪伴。复用现有 `_is_crisis_vigilant()`。

### 6.5 前端改动

`app/(tabs)/index.tsx` 现在的 `toggleConversation` 假设"会话由老人按按钮发起"。
主动招呼打破这个假设，但**不改变老人的心智模型**——他仍可随时按按钮。

改动集中在：

- 定时器（前台常驻）
- 沉默计时器（排除 6.3 的两个区间）
- 主动开口播完后自动进入录音态
- 无人应答收场

老人在 AI 主动说话时开口打断，走已有的语音打断逻辑（`3eddf5f`），不用新做。

## 7. 架构与组件边界

### 7.1 新增模块

| 模块 | 职责 | 依赖 LLM | 可单测 |
|---|---|---|---|
| `services/profile_service.py` | slot 状态机、存储、半衰期、优先级 | 抽取需要 | 状态机部分**完全纯逻辑** |
| `services/elicitation.py` | 采集规划器：这轮该不该采、采哪个 | 否 | **完全纯逻辑** |

**采集规划器是纯函数**：输入（画像状态、category、phase、危机标志、冷却计数、
`slot_hint`），输出（不采 / 顺水推舟某 slot / 主动起话头某 slot）。不调 LLM、
不碰 IO。这让 4.2 的两套门槛可以被穷举测试——本设计里最容易出错的逻辑，
恰好是最容易测的。

### 7.2 改动的现有模块

| 模块 | 改动 |
|---|---|
| `prompts/templates.py` | router 输出加 `slot_hint`；新增采集指令片段与主动开口 prompt |
| `services/llm_service.py` | `stream_reply` 消费 `slot_hint`；新增 `stream_proactive` |
| `routers/sse_llm.py` | 新增 `POST /llm/proactive` |
| `services/tts_service.py` | 读 `sensory_hearing` 调整语速/音量（3.4 的闭环） |
| `app/(tabs)/index.tsx` + hooks | 定时器、沉默计时器、自动开麦 |

### 7.3 存储

独立文件 `data/profiles/{elder_id}.json`，独立锁，**不塞进现有台账文件**。

理由：两者逻辑正交（台账是"合并叙事文本"，画像是"状态机推进"）。塞进同一个
文件就得共享锁和 `_load/_save`，而 memory_service.py 已经 440 行，再加一套
状态机会让它变成什么都干的模块。

沿用台账已有的**临时文件 + 原子替换**写法（`tmp.replace(path)`），以及
读取时的字段补齐（兼容早期文件）。

### 7.4 `elder_id`：一人一设备

**部署前提（已确认）：无论居家还是机构，都是一位老人一台设备。** 机构不存在
多人共用床头平板的情况。

因此 `elder_id` 绑定设备即可——首次启动生成并持久化到本地，之后每次请求带上。
不需要身份区分机制、不需要登录、不需要切换用户。

这个前提**不是实现细节，是安全前提**：如果它哪天不成立（比如出现共用设备的
部署），画像和台账会串到一起——把 A 的老伴说成 B 的，这在陪伴场景里是最伤人
的那类错误。所以它写在这里，而不是留在代码注释里。改变部署形态前必须回头
重新设计这一节。

## 8. 数据流

### 8.1 采集侧（每轮）

```
老人说话 --> ASR --> router(category + strategy_id + slot_hint)
                        |
                        v
                 采集规划器（纯逻辑）
                   - slot_hint 非空 且 非 crisis --> 顺水推舟
                   - slot_hint 空 且 安全窗口 且 有高优先级空 slot --> 主动起话头
                   - 否则 --> 不采集
                        |
                        v
              build_normal_prompt(策略 + 可选采集指令) --> Qwen --> 回复
                        |
                        v
              后台异步：从老人原话抽 slot 值 --> ProfileService 状态机推进
```

### 8.2 主动开口侧

```
触发（沉默计时器 / 定时器）
   --> 护栏检查（夜间静默 / 危机警戒 / 无人应答计数）
   --> POST /llm/proactive
   --> 话头选择（回指 > 画像空缺 > 寒暄）
   --> SSE 流出 --> TTS 播放 --> 自动开麦
   --> PROACTIVE_NO_ANSWER_SEC 秒无应答 --> 安静收场，无应答计数 +1
```

### 8.4 配置参数默认值

全部集中在 `config.py`，与现有 ASR/LLM/记忆参数并列。给出默认值是为了让实现
不必猜；这些值都需要实机调，但要从一个有理由的起点开始调。

| 参数 | 默认值 | 依据 |
|---|---|---|
| `ELICIT_MAX_PER_SESSION` | 2 | 见 4.3：一次对话 10-20 轮，再多就变味 |
| `ELICIT_COOLDOWN_TURNS` | 5 | 配合上一条，把 2 次采集撑开到整段对话里 |
| `ELICIT_MAX_ASK_COUNT` | 2 | 见 5.4 沉默即拒绝，超过即 `declined` |
| `SILENCE_PROMPT_SEC` | 25 | 见 6.3。远长于 `ASR_SILENCE_FRAMES` 的 1.5 秒断句阈值，量级估计，实机调 |
| `PROACTIVE_NO_ANSWER_SEC` | 20 | 略短于沉默唤起——没人应答时不该比有人时等更久 |
| `PROACTIVE_NO_ANSWER_GIVEUP` | 2 | 连吃两次闭门羹就停手；宁可少说 |
| `PROACTIVE_MAX_PER_DAY` | 3 | 早中晚各一次的量级，超过就是打扰 |
| `PROACTIVE_QUIET_HOURS` | 21:00-07:00 | 见 6.4(b)，硬边界，不受作息字段影响 |
| `OBSERVE_MIN_TURNS` | 20 / 30 | 见 3.2 各观察字段的最小样本量 |

### 8.3 关于抽取调用：一次还是两次

本期采用**独立调用**：ProfileService 自己发一次后台抽取，与 memory_service 的
`_extract_facts` 并行。

- 优点：两个服务完全解耦，各自可独立测试与失败
- 缺点：老人每句话触发两次后台 LLM 调用。一小时 120 轮的对话 = 240 次

两者都在后台、不占关键路径，对话延迟不受影响。**如果后续成本或速率限制成为
问题**，可以合并成一次调用（扩展 `EXTRACT_SYSTEM_PROMPT` 输出增加 slot 字段），
由 `llm_service` 编排分发给两个服务。届时再做，符合 YAGNI。

## 9. 错误处理

沿用现有原则："记忆是增强能力，抽取失败不该影响对话本身"
（memory_service.py 的既定做法）。

| 失败点 | 处理 |
|---|---|
| 画像抽取 / 存储失败 | 记 warning，不影响对话 |
| `slot_hint` 缺失或非法 | 当作空，本轮不采集 |
| 画像文件损坏 | 按空画像处理（台账已有此模式） |
| 主动开口 LLM 调用失败 | **静默放弃，不重试**——不能因为失败就反复出声 |
| 定时器在 App 后台/设备休眠时错过 | **不补发**。否则 App 回前台时会一次性说三段话 |

## 10. 测试策略

### 纯单元测试（不需要 LLM，离线可跑）

- **slot 状态机**：`unknown --> asked --> filled`；`asked --> declined`；
  `ask_count >= 2` 自动降级；半衰期到期转 `stale`；永不过期字段不转 `stale`
- **采集规划器**：穷举 4.2 表中每个条件的通过/拦截；顺水推舟在敏感类别下
  放行、在 crisis 下拦截；一次会话 2 条上限
- **夜间静默窗口**：注入时间，边界值（20:59 / 21:00 / 06:59 / 07:00）
- **无人应答收场**：连续 `PROACTIVE_NO_ANSWER_GIVEUP` 次后当天不再尝试；
  当天主动招呼达 `PROACTIVE_MAX_PER_DAY` 次后不再触发
- **观察类字段最小样本量**：样本不足时不下结论

### 需要 mock 的测试

- router `slot_hint` 解析：并入现有 `selftest/test_llm_service.py` 的路由 mock 测试

### 手动实机验证

- 沉默唤起的时机是否自然（20-30 秒该取多少，需实机调）
- 定时招呼的第一句是否像招呼而不像查户口
- 顺水推舟在敏感叙事下是否真的不违和 —— **这条最需要真人验证，
  自动化测试测不出"违和"**

## 11. 未决问题

1. **常驻前台的可行性。** 定时招呼要求 App 常驻前台并能在后台被唤起。
   Expo / React Native 在目标平台（尤其 Web 端）的常驻能力与限制需要实测验证。
2. **沉默唤起阈值的具体取值。** 8.4 给的 `SILENCE_PROMPT_SEC = 25` 是量级
   估计的起点，必须实机调。对老人而言，被打断的代价远大于多等一会儿（这条
   判断已经写在 `ASR_MERGE_WINDOW_MS` 的注释里，同样适用），所以调错方向时
   宁可往长了调。
3. **观察类字段的统计口径。** 3.2 表里的方法是初版，需要跑一段真实数据后校准。
